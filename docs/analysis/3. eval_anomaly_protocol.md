# Phân tích protocol đánh giá anomaly — `scripts/3. eval_anomaly_protocol.ipynb`

Tài liệu giải thích notebook protocol: **định nghĩa metric chung**, **win rule so với ETS**, và cách ghi baseline máy đọc được cho các tầng Chronos / IF / ECOD.

Đọc kèm: [`rice_alert_prototype.md`](rice_alert_prototype.md), [`phan_tich_thiet_ke.md`](phan_tich_thiet_ke.md).

---

## 1. Bài toán notebook này giải quyết

| Mục | Chi tiết |
|---|---|
| Vai trò | “Trọng tài” — không train model mới, không vẽ cảnh báo vận hành |
| Input | `reports/alert_backtest/*_summary.json` (sinh bởi batch ETS trong `rice_alert_prototype.ipynb`) |
| Output | `reports/eval/baseline_ets.json` + bảng baseline trong notebook |
| Người dùng downstream | `compare_chronos_ets.ipynb`, `benchmark_if_ecod.ipynb` |

Không có nhãn anomaly thật → không dùng accuracy. Protocol thay bằng hai proxy:

1. **Độ nhạy** = synthetic multiplicative injection recall  
2. **Tải cảnh báo** = alerts/năm (`WARN` + `CRITICAL`)

---

## 2. Pipeline trong notebook

```
alert_backtest/*_summary.json
        │
        ▼
  mean_key_recall(x2.0, x0.5)
  trên so_luong & tri_gia
        │
        ▼
  baseline_ets.json  (+ bảng hiển thị)
        │
        ▼
  beats_baseline(candidate, baseline)  ← dùng lại ở tầng 2–3
```

Các hàm forecast (`mase`, `interval_coverage`, `pinball_loss`, `precision_at_k`) được **định nghĩa sẵn** để các notebook khác import/copy — ETS summary hiện chưa đủ `yhat` theo tháng nên phần forecast chưa đổ số trong baseline.

## 3. Metric detection

### 3.1. Synthetic injection recall

Từ prototype ETS: tại mỗi tháng có score, nhân giá trị thực bằng hệ số shock rồi xem hệ thống có vượt ngưỡng WARN không.

| Hệ số | Ý nghĩa nghiệp vụ |
|---|---|
| ×1.2, ×1.5, ×2.0, ×3.0 | Spike tăng lượng / trị giá |
| ×0.7, ×0.5, ×0.3 | Sụt mạnh |

Trên thang log, nhân \(f\) ≡ cộng \(\log f\) vào residual / khoảng dự báo — khớp cách Chronos inject.

### 3.2. Key recall

\[
\text{key\_recall} = \text{mean}\big(\text{recall}_{so\_luong}(×2),\ \text{recall}_{so\_luong}(×0.5),\ \text{recall}_{tri\_gia}(×2),\ \text{recall}_{tri\_gia}(×0.5)\big)
\]

Chỉ lấy **×2 và ×0.5**: đủ lớn để “đáng bắt”, chưa cực đoan như ×3 / ×0.3 (gần như mọi phương pháp đều ~1.0).

### 3.3. Alerts / năm

Đếm tháng `WARN` hoặc `CRITICAL`, chia cho số năm lịch sử trên chuỗi. Đây là proxy **false-alarm / tải vận hành** khi không biết tháng nào là anomaly thật.

---

## 4. Win rule (candidate vs ETS)

Candidate **thắng** baseline chỉ khi **cả hai** điều kiện đúng:

1. `candidate_key_recall − baseline_key_recall ≥ 0.05`  
2. `candidate alerts/năm ≤ 2 × baseline alerts/năm`

Hàm `beats_baseline()` trả về `better_recall`, `rate_ok`, `wins` — cùng logic được copy sang notebook Chronos và IF.

### Vì sao rule hai điều kiện?

| Chỉ tối ưu… | Hệ quả xấu |
|---|---|
| Chỉ recall | Model “kêu liên tục” (Chronos-Bolt: recall ~0.94 nhưng ~3.85 alerts/năm) |
| Chỉ giảm alerts | Model “câm”, bỏ sót shock (IF: alerts vừa phải nhưng key recall thấp hơn ETS) |

Ngưỡng +0.05 và ≤2× là **hợp đồng thử nghiệm**, không phải định lý — đủ cứng để chặn cả hai cực, đủ nới để cho phép cải thiện thực sự.

## 5. Kết quả baseline ETS (đã chạy)

| Chuỗi | WARN+CRIT/năm | Key recall |
|---|---:|---:|
| dầu thô | 1.00 | 0.360 |
| gạo | 0.15 | 0.457 |
| sắt thép các loại | 0.46 | 0.764 |
| xăng dầu các loại | 1.08 | 0.762 |

Gạo có alerts/năm thấp nhất → win rule trên gạo **khắt khe về rate** (2× chỉ còn 0.30 alerts/năm). Đó là lý do Chronos dễ fail `rate_ok` dù recall cao.

## 6. Quyết định thiết kế đáng nhớ

| Quyết định | Lý do |
|---|---|
| Không generate `.md` bằng code trong notebook | Báo cáo narrative giữ ở `docs/` / `reports/eval/*.md` viết tay; notebook chỉ ghi JSON |
| Copy helpers vào mỗi notebook so sánh | Mỗi tầng tự chứa (Run All), không phụ thuộc package nội bộ |
| Key factors cố định `{x2, x0.5}` | So sánh công bằng giữa ETS / Chronos / IF |
| Đọc summary sẵn có, không re-run ETS | Tách “huấn luyện baseline” khỏi “định nghĩa luật so sánh” |

## 7. Cách chạy lại

1. Chạy batch ETS (`rice_alert_prototype.ipynb`, `RUN_BATCH=True`) nếu chưa có `*_summary.json`.  
2. Mở `scripts/3. eval_anomaly_protocol.ipynb` → Run All.  
3. Kiểm tra `reports/eval/baseline_ets.json` trước khi chạy tầng 2–3.
